### 单 NUMA 权重 alias:流式 prefill 从 5min → 20s(kt-kernel `moe.hpp` 改)
**现象**:本机流式 prefill 每次 ~5min(参考机 20s)。**根因不是 CPU**,是**内存被 CPU MoE 的匿名权重拷贝占满、GGUF page cache 装不下**:
- kt-kernel `LLAMA_MOE_TP::load_weights`(`operators/llamafile/moe.hpp`)会把 GGUF 权重按 TP(=NUMA 数)**gather-memcpy 进各 NUMA 本地匿名 buffer**。多 NUMA 时每节点拿 intermediate 的一条**跨步切片**,拷贝是真·重排、不可省;
- **单 NUMA(tp_count=1)时 `offset==0 && intermediate==complete`,这个拷贝退化成逐专家 identity 复制**——拷出来跟源 mmap 逐字节相同,纯浪费 ~138GB 匿名内存;
- 实测:改前 `RssAnon=140GB` / `buff/cache=62GB`(GGUF 138GB 只缓存一半)→ streaming 每次从 ext4 盘重读几十 GB;dedup(`KT_MXFP4_GGUF_DEDUP`)本意就是"streaming 复用 CPU 已在 DDR 的那份 mxfp4",但因 CPU MoE 是拷成匿名而非用 mmap,共享不成立。参考机只是 RAM 够大、两份都放得下才没暴露。

**修法(已提交)**:`load_weights` 加 identity 短路——`tp_count==1` 时 `delete[]` 掉 ctor 惰性 `new` 的预留(未写=无 RSS),把 `m_local_{gate,up,down}_proj_` **直接指向源 GGUF mmap**(`config.*_proj`),加 `m_weights_aliased_` 标志守卫析构。权重加载后只读(forward 只取址、`KT_DYNAMIC_RESIDENT` 只改 NPU mask 不写 CPU buffer),alias 只读 mmap 安全;多 NUMA 走原拷贝路径,零回归。

**效果(实测)**:`RssAnon 140GB→2.2GB`、`buff/cache 62GB→191GB`(138GB GGUF 全量缓存)、输出仍 `255`/`Paris`、长 prompt(5151 tok)**page cache 热时 19.8s** = 参考机水平。

**预热(内置 warmup;真因是 proxy 把 warmup 请求拦崩了)**:`p27_launch` 在 `KT_PREFILL_STREAM=1` 时**默认 `SKIP_WARMUP=0` + `KT_STREAM_WARMUP=1`**(开机 warmup 那发强制走 hybrid,既 prime kt_kernel、又消耗掉 `KT_STREAM_WARMUP` 预算,使首个用户请求正常 stream 而非被强制 hybrid)。
- **之前被迫用 `SKIP_WARMUP=1` 关预热的真正原因**:本机 `http_proxy=127.0.0.1:7890`,sglang 开机 warmup 会**对自己端口发 HTTP**,被 proxy 拦成 **502** → `warmup error: AssertionError res=<Response [502]>` → `Initialization failed` 直接退出。**修法:launcher 里 `unset http_proxy https_proxy all_proxy ...`**(本地推理服务不需要 proxy;顺带省掉 curl 的 `--noproxy`)。unset 后 warmup 正常,**首发长 prompt 22.5s、之后 19.9s**(不再 58.8s 被强制 hybrid)。
- **alias 的配套(madvise)**:alias 去掉了 load 时 memcpy,那次 memcpy 原本顺带把 138GB 读进 page cache;故在 `load_weights` alias 短路后对 mmap 做 `madvise(MADV_WILLNEED)` 异步 readahead,load 阶段后台暖 cache、不阻塞不拷贝。**注意**:`MADV_WILLNEED` 是建议性的,内核会限流(实测暖到 ~52G 就 plateau),且本机盘只有 **~0.38GB/s**,暖满 138GB 是 **~6min 的磁盘硬限**,谁都突破不了 —— 但 alias 保证了"暖一次就常驻",不再像改前那样每次 prefill 都冷读。冷 cache 验证:`sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches'`。
> 改 `moe.hpp` 后须**重编 kt-kernel**(`CC=gcc-13 CXX=g++-13 CPUINFER_ARM_{SVE,BF16,I8MM}=OFF … setup.py build_ext --inplace`),见主文档 §1。

## 1. 版本错配是根因(关键认知)
- 本仓 sglang 子模块 = `wenxuewuhd/sglang-dsv4 @ 4ea20e5d`。其 DeepSeek-V4 NPU 代码全部来自**一个 4 月 17 的 commit `c00daab08`**("Deepseek v4 support on NPU")。

## 3. 已确认"不是 bug"(排除)
子代理逐项核对 fork vs cann-recipes vs golden,以下**已验证一致**,不用再动:
- **交织 single `state_cache` 布局**:fork `[page,page_size,2,head_num=1,head_dim=coff*d]` reshape 后 = `[…, 2*coff*d]` = `[kv(coff*d)|score(coff*d)]`,与 cann-recipes `create_state_cache=[…,2,overlap_num=coff,cache_dim=d].flatten(-3)`、golden 打包**字节一致**。
- **fp32 `norm_weight`/`rope_cos`/`rope_sin`**:公开算子 dtype 支持表就是 DT_FLOAT,`.to(float32)` 对。
- **`cache_mode` 省略**:算子默认 1 == cann-recipes 显式 1。
- **MLA prolog**:**我们的 W8A8 权重 config 是 per-token dynamic int8 对称、且 safetensors 里没有任何 `smooth_scale*`**;cann-recipes 的 `npu_rms_norm_dynamic_quant(smooth_scale=wq_b.smooth_scales)` 在无 smooth_scales 时退化成普通 per-token dynamic int8 —— 和 fork 的 `q_norm→wq_b` 非融合 linear **同数学**。DSA 路径根本不走 `npu_mla_prolog_v3`(那个在 MHA 路径,fused-prolog 时 raise NotImplementedError)。
- decode 的 sparse-attn / SAS+LI metadata / quant_lightning_indexer 输入均与 cann-recipes 一致。

## 4. 真实差异清单(按乱码可能性排序)与进展

### #2 【修复中】prefill PA sparse-attn 的 `ori_kv` 用 kv_pad 但配 swa 块表 —— 源↔索引不匹配
`ascend_backend.py:1596-1623`(`USE_PA_PREFILL=1` 路径):`ori_kv=get_swa_buffer()` 算了却丢弃,实际传 `kv_pad = k.unflatten(0,(-1,page_size))`(当前 token 的 K,连续 `[num_pages,page_size,…]`),但 `ori_block_table=swa_page_table`(swa 池物理块号,受 dummy slot 0 偏移)→ 越界/读错行。
- 根因:**prefill 的 `set_kv_buffer` 在 sparse_attn 之后(~1773)**,所以此刻 K 还没进 swa 池 → 只能用 kv_pad;但块表却用了池的号。decode 路径(1678/1694)K 已在池里,用 `swa_buffer+swa_page_table` 是对的。
- **已做的尝试**:给 kv_pad 配 **identity 块表** `torch.arange(kv_pad.shape[0]).view(1,-1)`(逻辑页 i→物理页 i)。单请求 prefill 正确;多请求/多页需按 cu_seqlens 分段(待完善)。**待验证是否消除乱码**。
- 备选更彻底的修法:把 swa 的 K 写**挪到 sparse_attn 之前**,prefill 也用 `swa_buffer+swa_page_table`,和 decode 统一。

### #5 【待验证】compressor 的 cos/sin 只在 layer 2/3 填缓存(`nsa_indexer.py:436-445`)
只有 layer_id==2(首个 c4)/==3(首个 c128)调 `get_cos_sin_with_c*_cmpposition` 填 `rotary_emb.c*_cmp_position_*_layer_cache`,其余 c4/c128 层直接读该缓存。**仅当 `self.rotary_emb` 跨层共享才对**(`get_rope_wrapper` 需返回 cached/shared 实例);若 per-layer 实例,>3 层读到 stale/空 cos → 乱码。参考 fork 能跑通说明大概率共享,但**未最终确认**。

### #1 【本测试不受影响,需修以支持 prefix】prefill `start_pos` 写死 0(`ascend_backend.py:867-870`)
`start_pos=torch.zeros(bs)`、`seqused=None`,直接喂 compressor。cann-recipes 是 `start_pos=position_ids[:,0]`(=prefix_len)。对"从头单块 prefill、无 radix cache"(我们的 15×17,`disable_radix_cache=True`)**start_pos=0 是对的**,所以**这个测试不受影响**;但有 prefix cache / 多块 prefill 时会错。修:`start_pos=extend_prefix_lens`。

### #4 【待验证】c4/c128 state 块表对 overlap-read 区间的覆盖
fork 用全量分页 state 块表,cann-recipes 用 ring 表。`cache_mode=1` 下只要求算子会读到的每个 seq 位置(`copy_start_seq_id…end`,含 `start_pos//ratio*ratio - ratio` 的前一 overlap 块)都映射到**有效(非 0)块**;需确认 `req_to_token_c4_state` 在 overlap-read 范围都填了,否则读到 pad-block 0 → 乱码。

### #3 【大概率无害】decode 也走 TND(传 cu_seqlens+seqused)vs cann-recipes BSND
fork decode 也传 cu_seqlens 使算子进 TND 模式;经核对与 BSND 在对齐长度下结果一致,风险低。
