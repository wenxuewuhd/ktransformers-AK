# 精度与测量：结论是怎么建立的，以及每条结论有多硬

本文讲这条线上的数字是怎么来的、能支撑什么、不能支撑什么。
系统为什么长这样看 [`DESIGN.md`](./DESIGN.md)，怎么用看 [`README.md`](./README.md)。

**如果只读一段**：这个部署的精度判据不是 GSM8K，是**困惑度**——因为 GSM8K 在这里的
分辨率是 ±1.3pp，而我们要区分的差异比它小一个量级。而困惑度之所以能用，是因为它在
这条路上的**运行间噪声地板恰好是零**。

---

## 1. 判据阶梯

⚠ **"输出逐位相同"在本机只在 batch 宽度固定时才是合法判据。** 实测：同一 build、
同一提示，只把 decode 宽度从 1 改成 8，贪心输出就分叉（一条在第 16 个 token，
另一条在**第 0 个**）。组批是调度器决定的，跨运行不可复现。

所以判据按这个顺序，**不能只靠最后一条**：

1. **静态张量 `torch.equal`** —— 常驻专家搬上 NPU 后逐位对，带正/负对照。
   与 batch 无关，最硬。
2. **GGUF 逐位验证** —— 源 safetensors 反量化 == GGUF 块反量化。42/42 层通过。
3. **逐 token 分布判据** —— 困惑度 / MMLU 单 token。**比 GSM8K 锐利得多**。
4. **GSM8K 全量** —— 粗筛。

**GSM8K 基线**（1319 题，thinking 开，temp 1.0 / top_p 0.95）：BF16 TP16 97.35%；
INT8 W8A8 TP8 四轮 97.42 / 97.65 / 97.42 / 97.35。单轮二项 SE ≈ **±0.47pp**，
**96.5–98.4 都算一致**。

⚠ **这个判据排除不了小于约 1.3pp 的真实退化**——所以第 1、3 条不能省。

⚠ **短 prompt 不算数**：`seq_len < index_topk=2048` 时 DSA indexer 全选，稀疏路径
根本没走。"Paris 答对"在一个坏得很厉害的服务上也会过。`verify.sh` 因此用
>2048 token 的 prompt。

## 2. 为什么是困惑度

⚠ **GSM8K 和 MMLU 都测不到流式路径。** 流式的门是 chunk ≥ 512 token，而实测：

```
GSM8K       prompt ~60-120 token       流式不触发（inline resident 0）
MMLU 0-shot median 62,  max 110        0/50 越过门槛
MMLU 5-shot median 408, max 456        0/50 越过门槛  ← 连标准 5-shot 都不够
```

困惑度用 4096 token 的窗口，远在门槛之上，**是唯一真正跑到标准配置的判据**。

而且 GSM8K 会**吸收**分布误差：一个错 token 在 250 个 token 的推理里会被纠回来。
teacher-forced NLL 什么都不吸收，且每个 token 给一个数而不是每题给一个数。

### 噪声地板是零，这不是近似说法

不是"两次打印的小数位一样"，是 `nll_sum` 的 float **完全相等（0 ULP）**。
而且这个性质比最初以为的强得多——本轮清理中反复验证，它对以下全部不变：

- 服务重启
- `--max-running-requests` 1 → 8
- 不同 worktree、不同 die、不同 NUMA 对、不同端口、有无绑核
- 相隔 21 小时
- 清理过程中的**每一步**代码改动

**推论：困惑度不需要重复跑。** 每一秒都该花在更多窗口或对比臂上，重复是纯浪费。

### ⚠ 窗口数是内容差异，不是噪声

同一配置：3 窗给 2.2445、12 窗给 3.1449、32 窗给 3.5888。
**引用绝对值必须带窗口数，不同窗口数的两个数不能比。**
少窗口的前缀不代表全集——当晚差点据此误判。

## 3. 标准配置的代价：一笔交易，不是纯赢

流式 prefill + 动态热专家 vs hybrid：

| | hybrid | 流式 + dynamic hot | 变化 |
|---|---|---|---|
| **TPOT** | 19.28 tok/s ±0.12 | 23.13 tok/s ±0.93 | **1.200× ±0.017**，95% [1.166, 1.233] |
| **TTFT** @13933 tok | 208.36 s | 63.93 s | **3.26×** |
| **TTFT** @630 tok | 11.4 s | 18.3 s | **0.62×（更差）** |
| **困惑度**（32 窗，配对）| 3.548803 | 3.588837 | **+1.13%**，32 窗中 26 窗更差 |
| GSM8K（200 题）| 97.0 / 98.0% | 97.5% | 不显著（McNemar χ²=0.00）|

作为标尺：「全部专家换 MXFP4」实测 PPL +8.04%，所以这 1.13% 约是它的七分之一。

⚠ **两臂的 chunk 大小不同**（流式 6144 / hybrid 8192，各自的默认值，hybrid 没有那个
OOM 问题）。**这是"按部署配置比"，不是"控制单一变量比"。**

⚠ **TTFT 对短 prompt 是负收益**，交叉点实测约 1100 token。
`TTFT ≈ chunks × 18.0 s + 0.49 ms/token`，主项是 chunk 数不是 token 数。

## 4. TPOT 那一行被改了三次，每次都是方法学

这一行的历史值得留着，因为三次修订没有一次是"模型变了"。

**第一版**：`22.5 tok/s / +15%`——**一个点比一个点**，不确定度从未被界定。

**第二版**：空机器上重测同一配置拿到 20.66 / 21.84 / 22.37（跨度 7.9%），
说明重复性从未被界定，于是改成区间并声明"区分不了 1.05× 和 1.15×"。

**第三版（当前）**：A B A B 交错四轮，全部 `verdict: clean`、`foreign=0`：

```
dynhot   23.24 / 23.04 / 22.03 / 25.11    mean 23.35   sd 1.28  (5.5%)
hybrid   19.33 / 19.25 / 19.14 / 19.44    mean 19.29   sd 0.13  (0.7%)
                                     比值 1.211× ±0.033，95% [1.145, 1.276]
```

⚠ 真实收益**比原先声称的 1.15× 还高**，95% 区间排除了 1.05×。
撤回 +15% 在程序上是对的（单点撑不起一个比值），但当时顺带写下的"可能只有 +5%"
是错的方向。**教训不是"原来的数字是对的"，而是没有重复性的数字无论偏高偏低都不该被引用。**

⚠ **两臂离散差 8 倍**（hybrid 0.7% vs dynhot 5.5%）不是偶然：dynamic hot 每次 prefill
都按当次直方图重选常驻集，hybrid 用固定的静态 prefix——**变的那一臂正是有自由度的那一臂**。
机制合理但未验证。**引用 dynamic hot 的 TPOT 必须带离散**，单次运行可能落在 22.0–25.1。

## 5. 测量纪律（每条都是拿时间换来的）

**2026-08-31，所有单 NUMA 的吞吐数字一次性作废。** 邻居的作业在测量中途占满了 die，
而受污染的三个点**画出了一条很像样的饱和曲线**（8→16 只有 1.25×，16→32 只有 1.08×）。
据此下的"单节点内存带宽墙"结论已撤回。⚠ 它可能仍然是对的，但它不再是证据。
真正的原因是 NUMA 页放置（见 [`DESIGN.md`](./DESIGN.md) §4）。

教训做成了工具而不是靠自觉：**`bench.sh` 的门禁不过就拒绝出数**——外来 sglang 进程数、
目标 die 的 HBM 回落、`Load weight begin. avail mem=`（撞车会在这里现形，**远早于**它
表现成"跑得慢"）、跑完再查一次 load。每个结果连同这些一起写进 JSON。

其余几条在 [`README.md`](./README.md) 的「测量纪律」里，最要紧的两条：
**`wall/generated_tokens` 不是 decode 速率**（TTFT 被折进去了），
**单点不是测量**（同配置重复跑离散 5.7%，A/B 两臂要交错）。

## 6. 判据体系照不到的那块

四道判据按锐利度排是 A1（困惑度逐位）> A2（启动命令逐字节）> A3（验收冒烟）> A4（吞吐）。
**这个排序本身会鼓励省事，而它两次都错了：**

**第一次是覆盖面。** A1 的窗口是 4096 token = 单 chunk，所以它**看不见**一个
"任何超过一个 chunk 的 prompt 都会 OOM"的配置——那期间 A1 全程绿灯，是 A3 那道
"粗糙"的冒烟门先撞上的。⚠ **A1 最锐利，但它的覆盖面很窄；它证明不了长 prompt 能跑。**

**第二次是性质。** 清理中一度把后台池排空判据改成一个自引用的表达式，使排空发生在
第一层而不是最后一层，把"后台读与模型加载重叠"这个优化整个空转掉。
**四道门当时全是绿的**：A1 不改数值所以逐位相同、A4 是 decode 窗口而这是加载期、
A3 照样起得来只是慢、A2 命令行没变。抓到它的是**读代码时注意到注册表的填充顺序**。

⛔ **所以：四道门证明的是「行为没变」，而一个把优化空转掉的改动，行为恰恰没变。
它们不能替代 review。**

还有一条独立的：**"判据会通过"和"判据会失败"是两件事**。
`test/registered/moe/test_kt_stream_resident_commit.py` 做过变异测试——把
`_abort_resident_commit` 变成 no-op（即重新引入它防的那个 bug），两个 hazard 场景立刻红，
负对照仍绿。**一个从没被证明会失败的回归测试是空门。**

## 7. 还没有干净数据的

- **`KT_MXFP4_DEPOOL=0` 的代价**：那条臂的 reader 已删除，此项作废。
- **混合负载的状态依赖**：短 prompt 不触发流式因此不重置常驻集，一个短请求会继承
  前一个长请求装好的热专家。**未测。**
- **`--chunked-prefill-size` 调大**：TTFT 主项是 chunk 数，这是最大的一根杠杆。
  ⛔ 但反方向先撞了墙——流式默认的 8192 会让 KDA 的 ~3 GiB workspace OOM，
  默认已降到 6144。要调大必须先在别处腾显存。**未测。**
- **`GLM53_PIN_CORES` 在 NUMA node ≥4 上致命**：已自动跳过并告警，**根因未修**。
